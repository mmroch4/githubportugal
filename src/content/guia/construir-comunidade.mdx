## Dar a conhecer o projeto

Um projeto que ninguém conhece não recebe contribuições. Algumas formas de o divulgar:

- **Partilha-o nas comunidades certas.** Fala dele no [Discord](https://discord.com/invite/cnJdppDkUp) do GitHub Portugal e nas **[comunidades tech portuguesas](/comunidades)** ligadas à tecnologia que usas.
- **Apresenta-o num evento.** Meetups e conferências procuram muitas vezes oradores. Vê a **[agenda de eventos](/eventos)** e propõe uma palestra curta sobre o problema que o projeto resolve.
- **Escreve sobre ele.** Um artigo a explicar porque criaste o projeto e como funciona atrai mais interesse do que um simples link.
- **Adiciona-o ao [diretório de projetos](/projetos)** do GitHub Portugal.

Explica sempre o problema que o projeto resolve, não só o que ele é. As pessoas interessam-se por soluções para os seus problemas.

## Acolher quem chega

A primeira experiência de alguém com o teu projeto decide se essa pessoa volta. Algumas boas práticas:

- **Responde depressa**, mesmo que seja só para dizer "obrigado, vou ver isto na próxima semana". Um silêncio de semanas afasta as pessoas.
- **Agradece todas as contribuições**, incluindo issues bem escritas e correções pequenas.
- **Sê paciente com quem está a começar.** Se um pull request precisa de alterações, explica o que falta e porquê, e dá exemplos.
- **Tem tarefas prontas para novas pessoas.** Issues com a etiqueta `good first issue`, bem descritas e com indicação dos ficheiros a alterar, são o melhor convite.
- **Aplica o código de conduta.** Se alguém for desrespeitoso, age de forma rápida e consistente. Uma comunidade segura é uma comunidade que cresce.

## De utilizadores a contribuidores e mantenedores

A maioria das pessoas começa por usar o projeto. Algumas reportam problemas, e algumas destas acabam por contribuir. Podes ajudar a fazer essa caminhada:

- **Documenta como as decisões são tomadas.** Um ficheiro `GOVERNANCE.md`, ou uma secção no README, diz quem decide e como se chega a novos mantenedores.
- **Reconhece o trabalho das pessoas**, por exemplo nas notas de cada versão ou com uma lista de contribuidores no README.
- **Dá responsabilidades a quem contribui com regularidade.** Convida-as a rever pull requests, a fazer a triagem de issues e, mais tarde, a ser mantenedoras.
- **Tem um sítio para conversar.** O separador **Discussions** do GitHub serve bem para dúvidas e ideias que não são issues.

## Comunicar em português ou em inglês?

Depende do público. Se o projeto é útil para pessoas fora de Portugal, escrever o código, as issues e a documentação em inglês alarga muito a comunidade possível. Se é pensado para o contexto português (por exemplo, uma biblioteca para validar NIF ou para trabalhar com dados públicos portugueses), escrever em português torna-o mais acessível a quem o vai usar. Também podes ter o código em inglês e a documentação nas duas línguas.

Quando tiveres pessoas à volta do projeto, chega a altura de pensar em como o manter de forma sustentável: vê as **[boas práticas de manutenção](/guia/boas-praticas-de-manutencao)**.
